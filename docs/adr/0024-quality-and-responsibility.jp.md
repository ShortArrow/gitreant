# ADR 0024: 品質ゲートを3段階に定め、提供責任を4本柱で明文化する

## Status

Accepted (2026-07-24)

## Context

テストは unit（cargo test --lib / vitest）・統合（cargo test）・E2E
（Playwright 直列1本、10〜17分）・スクリーンショット生成時の機能
アサーションの4層に育ったが、どれをいつ必須にするかは暗黙運用
だった。特に E2E は実行コストが高く、複数機能が未実行のまま溜まる
実態があり、層間の取りこぼし（例: stash_internal がシリアライズ
されず折り畳みが一度も効いていなかった件）を許した。

また gitreant が「何に責任を持ち、何を持たないか」——localhost 限定の
信頼境界、リポジトリへ加えてよい操作、gh/gpg 欠如時の挙動、外部への
送信——が文書化されておらず、機能追加のたびに判断が揺れていた。

## Decision

- **品質ゲートは3段階とする。**
  1. 毎 push: backend 全テスト・frontend の tsc / vitest / build を
     green にする。バグ修正は再現テストを先に書く（Red→Green）。
  2. 機能マイルストーン毎（UI 機能のまとまりが完了した時点）:
     E2E フルスイートを実行して green にしてから次へ進む。
  3. リリース/タグ前: E2E フルに加え `pnpm screenshot` の
     アサーション（README 掲載機能の可視回帰）を green にする。
- **提供責任は4本柱で明文化する**: 信頼境界・データ安全・外部依存の
  劣化動作・ネットワーク送信の列挙。運用詳細は
  [docs/QUALITY.jp.md](../QUALITY.jp.md) を単一ソースとする。
- 破壊的 git 操作（履歴改変・強制 push・削除系）の追加は
  QUALITY.jp.md の改訂と ADR を要する。

## Consequences

- E2E 未実行の機能が複数溜まったら、それはマイルストーン完了の
  合図であり、フル実行してから次の機能に着手する。
- スクリーンショット生成が機能の「見えている」ことの回帰試験を
  兼ねるため、README 掲載機能を壊すとスクリーンショットが失敗する。
- 責任範囲に関する問い合わせ・判断は QUALITY.jp.md を参照先とし、
  そこに無い保証は「していない」と答えられる。
