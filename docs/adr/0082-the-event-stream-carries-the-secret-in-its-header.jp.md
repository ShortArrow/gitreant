# ADR 0082: イベントのストリームも秘密をヘッダで持つ

## Status

Accepted (2026-11-05)。[ADR 0063](0063-request-token.jp.md) を改める。

## Context

ADR 0063 では、API のすべてのリクエストがサーバの秘密を `X-Gitreant-Token` ヘッダで持つ。例外は「ブラウザがヘッダなしで開くイベントのストリーム」で、クエリの `token` で持っていた。ページがこのストリームを、ヘッダを付けられない `EventSource` で開いていたためである。

このクエリは、アドレスバーとブラウザの履歴には出なかった。一方で、ページのリクエストを記録するものには残った。別の場所で読むためにファイルへ書き出したページの Lighthouse レポートには、まだ有効な秘密とともに `/api/events?token=<secret>` が入っていた。開発者ツールと、そこから書き出すリクエストの記録にも同じように出る。秘密の受け渡しのほかの経路は、サーバに届くアドレスに秘密を載せないので（[ADR 0076](0076-post-the-secret.jp.md)）、残っていたのはここだけだった。

## Decision

- **ページはストリームを `fetch` で読む。** `frontend/src/eventStream.ts` は、ほかのリクエストと同じ `apiFetch` で `/api/events` を開く。そのため秘密はヘッダに載る。ストリームのテキストは自分で解析する。
- **サーバはクエリを読まなくなる。** 秘密をクエリにしか持たない `/api/events` へのリクエストには、ほかの経路と同じく 401 を返す。
- **ページが頼っている部分は `EventSource` と同じに動く。** 接続のたびに知らせ、切れたら、サーバが指定した `retry` か 3 秒のあとで接続し直し、サーバがエラーで答えたら止まる。

| 別の案 | 採らない理由 |
|---|---|
| `EventSource` のままで、クエリを受け入れる | 秘密が有効なあいだ、ページのリクエストの記録すべてに残り続ける |
| ブラウザがストリームに付けて送る cookie | cookie はオリジンのものだが、秘密はタブごとに保つ（[ADR 0073](0073-page-under-a-path-of-each-start.jp.md)） |
| 秘密で取得する短命のチケットをクエリに載せる | アドレス 1 つのために 2 つ目の認証情報とサーバの状態が増える。ヘッダならどちらも要らない |

## Consequences

- 接続のし直しは gitreant 自身のコードになる。切断、サーバが指定した待ち時間、拒否、閉じる動作はテストで確かめる。
- ストリームの 401 は、ほかのリクエストと同じくページに伝わる。再起動をまたいで開いたままのタブは、次のリクエストを待たず、ストリームが接続し直した時点で、サーバの秘密がないと表示する。
- パーサは、サーバが書く `\n` と `\r\n` で終わる行を読む。イベントストリームの形式が認めている `\r` 単独は、行の終わりとして読まない。
- 開発者ツールでリクエストの記録を読む人にはヘッダの値が見え、ヘッダ付きで書き出した記録にも残る。
