# ADR 0083: 裏の作業の区切りは、確定した結果を通知に載せる

## Status

Accepted (2026-11-16)。[ADR 0037](0037-deferred-signature-check.jp.md) と [ADR 0041](0041-diff-stats-per-commit.jp.md) を改める。

## Context

リポジトリを読むと、署名の確認（[ADR 0037](0037-deferred-signature-check.jp.md)）とコミットの行数の集計（[ADR 0041](0041-diff-stats-per-commit.jp.md)）が裏に残る。どちらも最大 256 コミットずつの区切りで進む。区切りが終わるたびに `verified` か `counted` の通知が出ていたが、通知はリポジトリを名指すだけだった。開いているページはそのたびに、そのリポジトリの view を読み直していた。読むたびに全履歴をたどってグラフを作り、そのあとでページが求めた行に切り詰める。そのため、区切り 1 つごとに、開いているページの数だけ全体を読み直していた。

2026-11-16 に、`main`（7d77945）のリリースビルドで zed（23,773 コミット）を Windows 11 上で読んだ。1 回の読み込みは約 0.5 秒だった。そのあとの区切りは 404 秒続き、行数の集計が 118 回、署名の確認が 45 回だった。zed を追加してから 45 秒のあいだに、ページ 1 つは view を 127 回読み直した。同じポートのページが 3 つあると 277 回になり、1 回の読み込みは最長で 0.55 秒から 11.6 秒に延びた。どの数字も 1 回だけの計測である。

## Decision

- **通知に区切りの結果を載せる。** `counted` は `{"repo": <id>, "commits": [{"id", "stat"}]}` を、`verified` は `{"repo": <id>, "commits": [{"id", "verified", "signature_key"}]}` を持つ。中身は、区切りの各コミットに、いま読めば付くものである。確認のあいだにキャッシュが消され、判定を捨てたコミットは載せない。
- **ページは書き足すだけで、読み直さない。** 区切りが確定したものをリポジトリとコミットごとに覚え、そのリポジトリの view に重ねる。重ねる先は、手元にある view と、あとから届く view である。区切りが確定したときにすでに送られていた読み込みは、その結果を含まずに返ってくるので、これにも重ねる。
- **`update` の通知で、覚えたものを捨てる。** それに続く読み込みは、読み始める前に確定したものをすべて含んでいる。また、再検証はサーバの判定を消すので、覚えた判定がそれより長く残ってはいけない。

| 別の案 | 採らない理由 |
|---|---|
| たどったグラフをサーバが読み込みのあいだ持っておく | 区切りのたびに、数個の値を変えるために、最大 500 行の view 全体（zed では約 360 KB）をすべてのページに送ることになる |
| 読み直しを 1 秒に 1 回までにする | 区切りが続くあいだ、読み込みはページごとに全履歴をたどり続ける |

## Consequences

- 区切りは読み込みを起こさない。ページが view を読むのは、リポジトリを開いたとき、スクロールで行を足すとき、`update` を受けたときである。
- 通知は大きくなる。区切りの最大 256 コミットぶんを、それぞれの id とともに持つ。
- 通知を取りこぼしたページは、`update` で元に戻る。サーバは、遅れた受け手に `update` を送る。
- テストでは、区切りが報告する行数と判定、動いているサーバが送る通知、結果を view に重ねることと、あとから届く view のために覚えておくこと、150 コミットの履歴を集計するページが view を 2 回より多く読まないことを確かめる。
