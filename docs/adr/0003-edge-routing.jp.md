# ADR 0003: レーンをまたぐエッジは1行分の曲線＋垂直線で経路する

## Status

Accepted (2026-07-09)

## Context

マージされたコミット同士の間に多数のコミットが挟まると、子ノードから親ノードまで全行スパンを1本のベジェ曲線で結ぶ従来の描画では、線がほぼ垂直の斜線（漸近線状）になり、どのレーンに属する線なのか識別できなかった。

既存ツールの解法を調査した結果、いずれも「長い線を斜めに引かない」方式だった。

- **VSCode Git Graph** (mhutchie/vscode-git-graph): 線はブランチに属するセグメント列で、垂直区間は直線、レーンをまたぐ区間だけ1行分の高さの曲線。
- **git-graph** (mlange-42/git-graph): 列を垂直に走り、折れ点となる行で水平（SVGでは曲線）に隣の列へ移る3セグメント構成。
- **GitKraken**（クローズドソース）: 画面上の挙動は同じ。線はレーン内を垂直に走り、合流・分岐する行でだけ短くカーブする。

## Decision

- レーンをまたぐエッジ（子 → 親）は、**子の行から1行分だけ曲線で `to_lane`（親のレーン）へ移り、残りは `to_lane` を垂直な直線で降ろす**。同一レーンのエッジは従来どおり垂直線、隣接行のエッジは曲線のみ。
- 経路計算はフロントエンドの純関数 `edgePath`（frontend/src/graph.ts） に閉じる。ドメイン層のレーン割当・エッジ表現（`from_lane`/`to_lane`）は変更しない。
- 曲がる位置は**子側の端**とする。ドメイン層の layout は未配置の親をレーンに保持し続けるため、`to_lane` の垂直回廊は子の行から親の行まで他のノードに使われないことが保証される（親側で曲げる場合、`from_lane` 側にはこの保証がない）。この不変条件はレンダラが依存する層間契約として `layout` の docstring（src/domain/graph.rs）にも明記する。

## Consequences

- 複数の子が同じ親にマージされる場合、垂直区間が同一レーン上で重なり「1本の線に合流して見える」。これは Git Graph と同じ正しい表現。
- layout のレーン再利用の挙動を変える場合（親配置前のレーン解放など）は、この描画契約が成り立たなくなるためエッジ経路の再設計が必要。
- git-graph が行う「折れ点行の挿入」や交差最小化の列割当は採用しない。SVG は行内で自由に曲線を引けるため行挿入は不要で、交差最小化は現状のレーン数では過剰と判断した。
