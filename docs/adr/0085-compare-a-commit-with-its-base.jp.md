# ADR 0085: コミットを、ベースから分かれたところから比べる

## Status

Accepted (2026-11-17)

## Context

pull request が示すのは `base...head` である。head が base から分かれてからの変更だけで、そのあとに base が得たものは含まない。コミットのメニューは、選択中の別のコミットとの比較を出していた（[ADR 0035](0035-graph-node-navigation.jp.md)）。これは 2 つのツリーをそのまま比べる `base..head` である。トピックブランチのコミットをこの方法でベースと比べると、トピックが分かれたあとにベースが得たものもすべて、逆向きに表示される。

## Decision

- **コミットのメニューに「ベースの \<branch\> と比較」を出す。** 差分は、そのコミットがそのブランチから分かれたところ（`git merge-base` が見つけるコミット）から、そのコミットまでである。pull request が示す 3 点の差分にあたる。
- **ベースは pull request と同じように選ぶ。** そのコミットを含むローカルのブランチのうち、先頭からの手数が最も少なく、開いた pull request を持つものが、ベースを決める。項目には pull request の番号も出す。そういうブランチがなければ、ベースは `origin/HEAD` が指すブランチ、なければ `main`、`master`、チェックアウト中のブランチの順で、最初にあるものにする。origin にだけあるブランチは、`origin/<branch>` として比べる。
- **ベースがすでにそのコミットを含むときは、項目を出さない。** 差分が空になるからである。ベースが見つからないときも出さない。
- **比較は、2 つのコミットを比べるときと同じ場所に出す。** 分かれたところを「\<branch\> との分岐点」と示す。分岐点は読み込み済みの行にあるとは限らないので、パネルに出す内容はサーバの答えが持つ。
- **サーバは `POST /api/merge-base` に答える。** リビジョンとコミットの分岐点を返す。pull request は base のブランチも持つ。

## Consequences

- コミットを含むブランチは、読み込み済みのコミットの中だけで探す（[ADR 0023](0023-progressive-loading.jp.md)）。そのため、先頭が読み込み済みの行より前にあるブランチは考えに入らない。
- pull request のないブランチのコミットは、既定のブランチが本当のベースでないリポジトリでも、既定のブランチと比べる。git-flow で `develop` から分かれた feature ブランチがその例である。
- テストでは、ベースの選び方、サーバが見つけて返す分岐点、ページの項目と比較を確かめる。
