# ADR 0038: ループバックのサーバ宛てで、自分のページから来たリクエストだけに応える

## Status

Accepted (2026-10-22)

## Context

サーバは 127.0.0.1 だけで待ち受け、それ以外にリクエストと API の間を隔てるものはなかった。ブラウザは、どのページにもこのサーバへのリクエストを送らせる。

- `POST /api/shutdown` と `POST /api/refresh` はボディを取らない。そのため、どのサイトのページも CORS の事前確認なしにこれらを送り、サーバを止めたり署名のキャッシュを捨てさせたりできる。
- DNS リバインディングでは、サイト自身の名前が 127.0.0.1 に解決される。するとブラウザはサーバをそのサイトのオリジンとして扱い、ページは API を読み、JSON のリクエストも送れる。チェックアウト、マージ、タグやブランチの作成と削除がこれに当たる。

JSON のエンドポイントがほかのサイトから守られていたのは、JSON の `Content-Type` には事前確認が要り、サーバがそれに応えないからにすぎなかった。

## Decision

- **Host。** すべてのリクエストは、`Host` ヘッダでループバックのホスト（`127.0.0.1`、`localhost`、`[::1]`）を名指す。ポートは問わない。ほかの名前には 403 を返す。リバインドされた名前はループバックの名前ではないので、DNS リバインディングはどこにも届かない。
- **Origin。** `GET` と `HEAD` 以外のリクエストが `Origin` ヘッダを持つときは、サーバ自身のオリジン（`http`、ループバックのホスト、サーバのポート）から来ていなければならない。ほかのオリジンには 403 を返す。`Origin` のないリクエストは通す。ブラウザはこの種のリクエストに必ず `Origin` を付けるので、ないのは gitreant の CLI のようなクライアントであり、それはどのみちポートに直接届く。
- **開発用のプロキシ。** `pnpm dev` は SPA を自分のポートで配り、API をプロキシする。プロキシは、gitreant が配ったページであるかのように、`Origin` をバックエンドのものに書き換える。

## Consequences

- 読み取りは、ループバックのどのクライアントにも開いたままである。このガードが扱うのは、よそから来たブラウザのページに何ができるかであり、ほかのローカルのプロセスではない。
- ループバックの別のポートで別のプログラムが配るページも、gitreant を操作できない。
- リスタートボタンのように、サーバの状態を変える Web の操作も、既存のエンドポイントと同じく守られる。
